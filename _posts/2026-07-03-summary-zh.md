## [crustc：将整个 rustc 编译器转译为 C 语言](https://github.com/FractalFir/crustc) ⭐️ 8.0/10

一位开发者发布了 crustc，这是三年工作的成果，它将整个 Rust 编译器（rustc）转译为 C 代码。作者称这是他们第 14 次尝试把 Rust 编译到 C，是在早先的 cilly 项目基础上完成的。 通过生成任何标准 C 编译器（如 GCC）都能构建的 C 代码，crustc 有望让缺少 LLVM 或 GCC 后端的老旧或冷门硬件也能支持 Rust。它还有助于解决自举问题，因为通常从源码构建 Rust 编译器本身就需要一个已有的 Rust 编译器。 该项目的主要目标是支持没有 LLVM/GCC 后端的硬件，并让 GCC 负责对生成的 C 代码进行优化。评论者指出，LLVM 自己的 C 后端曾长期不可用，但现在可能正在被恢复，而且转译到 C 通常被认为比针对 LLVM IR 更容易。

hackernews · Lobsters · 7月2日 22:57 · [社区讨论](https://news.ycombinator.com/item?id=48768464)

**背景**: rustc 是官方的 Rust 编译器，通常使用 LLVM 为受支持的 CPU 架构生成机器码。自举指的是一个先有鸡还是先有蛋的问题：编译一个用自身语言编写的编译器，需要预先存在该编译器的二进制文件。转译是指把源代码从一种语言翻译成另一种语言（这里是 Rust 到 C），而不是直接编译成机器码，这样标准的 C 编译器就能生成最终的二进制文件。

**社区讨论**: 社区对这三年原创、非 LLM 生成工作的投入表示钦佩，多位评论者称赞其确实令人印象深刻。技术讨论中有人提出用多重双重编译（Diverse Double-Compiling）来检测官方 rustc 是否存在后门，也有人质疑 LLVM 已恢复的 C 后端是否能达到同样的转译目的。

## [Linux 6.9 回归缺陷：LUKS 挂起不再从内存中清除加密密钥](https://mathstodon.xyz/@iblech/116769502749142438) ⭐️ 7.0/10

自 Linux 6.9（2024 年 5 月发布）起，`cryptsetup luksSuspend` 操作不再从内核内存中清除 LUKS 磁盘加密主密钥，这意味着系统挂起期间该密钥仍可能被恢复。 那些依赖挂起功能来保护加密磁盘的用户期望主密钥能从内存中被清除，因此这个回归缺陷削弱了对冷启动攻击和物理接触攻击的防护——攻击者若拿到设备便可能从内存中提取出密钥。 该问题影响范围有限，因为基于 `luksSuspend` 的密钥清除并非上游内核官方支持的功能，而是 Debian 实现的扩展（NixOS 也在使用），因此人们对这究竟是真正的内核缺陷还是发行版特定问题存在争议；NixOS 现已添加了一个测试用于捕捉此类回归。

hackernews · Lobsters · 7月2日 15:25 · [社区讨论](https://news.ycombinator.com/item?id=48763035)

**背景**: LUKS（Linux 统一密钥设置）是 Linux 上的标准全盘加密系统，它使用保存在内核内存中的主密钥来实时加解密磁盘内容。`luksSuspend` 命令的作用是在系统休眠时锁定加密卷并将其密钥从内存中移除，使得物理接触设备的攻击者无法转储内存来恢复密钥。这与挂起到磁盘（hibernate，休眠）不同——后者将内存内容写入磁盘并在唤醒时需重新输入密钥；也与挂起到内存（sleep，睡眠）不同——后者密钥通常仍驻留在内存中。

**社区讨论**: 评论者们争论这是否该归咎于内核，有人指出 `luksSuspend` 的密钥清除是 Debian 的扩展而非官方支持的功能，另一些人则厘清了睡眠（密钥留在内存中）与休眠（密钥被清除、唤醒时需输入密码）之间的区别；还有一位评论者在没有证据的情况下猜测这可能是有意植入的后门。

**标签**: `#linux-kernel`, `#disk-encryption`, `#security`, `#LUKS`, `#regression`

**背景**: 差分隐私是一种数学上严谨的技术，通过添加经过精心校准的随机噪声来保护数据集中的个体，使得在保持整体统计准确性的同时难以识别任何单个人。美国人口普查局在 2020 年人口普查中采用了差分隐私，以防范可能从已发布表格中重新识别个体的重构攻击。指令所允许的'粗化'技术则通过将数据归入更宽泛的类别来减少细节。Scott Aaronson 是一位著名的理论计算机科学家，以量子计算和计算复杂性领域的研究闻名。

**社区讨论**: 评论者展开了实质性辩论：有些人质疑 Aaronson 的表述过于修辞化或'夸张'，认为这个问题更多关乎数据实用性而非隐私，另一些人则想弄清该指令背后的政治动机。有评论者指出文章的行动号召缺少联系立法者的链接，并提供了一个。

hackernews · doener · 7月2日 11:17 · [社区讨论](https://news.ycombinator.com/item?id=48759634)

## [Postgres 事务是分布式系统的超能力](https://www.dbos.dev/blog/co-locating-workflow-state-with-your-data) ⭐️ 7.0/10

DBOS 的一篇博客文章提出，将工作流状态与应用数据放在同一个 Postgres 数据库中，可以用单个事务原子地同时提交业务数据和工作流进度，从而优雅地解决分布式系统中经典的双写（或 outbox）问题。 双写问题——在没有分布式事务的情况下让数据库和消息队列保持一致——是一个众所周知且确实棘手的分布式系统难题，因此一种用普通 Postgres 事务规避该问题的方法，可能会简化那些原本需要复杂 outbox 或事件溯源机制的架构。 该方法将每个工作流步骤与数据库提交单元一一对应，从而简化了 outbox 模式，但也让工作流状态与数据库紧密耦合，导致日后在架构上更难将两者分离。

hackernews · KraftyOne · 7月2日 18:38 · [社区讨论](https://news.ycombinator.com/item?id=48765639)

**背景**: 双写问题出现在一次操作必须原子地更新两个系统（通常是数据库和消息队列）时，但由于没有跨越两者的共享事务，一旦在两次写入之间发生崩溃就会导致数据不一致。outbox 模式是常见的变通办法：在与业务数据相同的事务中，把要发送的消息写入数据库中的一张表，再由独立进程读取并发布。事件溯源和预写日志是相关技术，它们把有序的变更日志作为唯一可信来源来实现一致性。

**社区讨论**: 评论者大多认同这个核心问题真实且棘手——有人回忆自己曾在面试中告诉面试官，在没有事件溯源等模式的情况下可靠地同时更新数据库和队列本质上是不可能的——同时有几位表示他们已成功使用类似的库内 pubsub 或故障保护方案；最尖锐的批评警告说，把工作流状态绑定到数据库会造成难以解开的耦合，还有一位持怀疑态度的人调侃这本质上只是围绕中心数据库的一把互斥锁，而非真正的分布式系统。

**标签**: `#distributed-systems`, `#postgres`, `#transactions`, `#workflow-orchestration`, `#database-architecture`
